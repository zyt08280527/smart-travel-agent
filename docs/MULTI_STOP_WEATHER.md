# 多站点逐站天气提示

2026-10-23：在“去哪玩”最小闭环之后继续核心功能，暂不扩景点或做上线准备。本阶段先为选定的多站点方案提供按需天气提示，不将未核验的天气权重加入路线评分。

## 入口与可信数据

正式多站点页面生成可行方案后，可点击“查询或刷新逐站天气”。前端只发送草案 ID、选中方案 ID，`POST /api/multi-stop/drafts/{draft_id}/weather` 从本地可信草案取逐站位置和时间，不接受客户端提交坐标、时间线或气象结果。

如果后来改选让旧方案不再出现在草案展示候选中，可通过该草案/方案对应的已保存完整快照读取原时间线。没有匹配的草案/保存快照时拒绝；不拿最新推荐替换旧方案。新增读取方法不改变数据库结构，也不修改草案或保存记录。

查询时刻使用当前选中方案各站的 `arrival_at`（等待结束后的有效到达时刻），不是所有实际到站/等待时间和停留期间的全量采样。第一站使用出发时刻，终点使用到达时刻。坐标是规划中归一化的 WGS84，天气来自周边预报网格，不是现场传感器观测或整段路线走廊天气。

## 供应商与时间语义

沿用 Open-Meteo 小时预报能力，新增面向可信坐标的逐站适配器，复用现有 HTTP 观测包装、供应商地址和 WMO 中文描述映射。没有修改原单段天气服务，也没有完成高德实况/按天天气迁移。

接口参数依 [Open-Meteo 官方文档](https://open-meteo.com/en/docs) 核对：明确摄氏度、毫米、km/h，以 Unix 时间戳读取小时数据，按北京时间日期请求，避免把无时区字符串猜成本地时间。最多尝试今天起 16 天窗口，实际覆盖以返回时间为准。

为处理接近午夜的到达时间，每个站点/日期请求当天及可查询范围内的下一天；相同坐标/日期在一次查询中复用结果（重复到访仍分行展示）。最多 5 个站点/5 组请求，并发上限 2，单请求 8 秒，整次天气补充 25 秒。过去时刻不查询历史天气，超出窗口不请求；不改查当前实况作为未来预报。

从返回小时中选取与目标时刻相差不超过 30 分钟的最近小时，等距时取较早时刻。展示预计到达时间、实际匹配的预报时刻、查询时间和来源，全部可转换为北京时间。

缺小时、时刻相差太远、单位不符、空指标、非有限值、负降水/风速、供应商错误及超时均保留“天气未知”。单点失败不清除其他点已取得的结果，不暴露原始异常和 URL。客户端中止或切换方案时隔离迟到响应；不保证断开 HTTP 后服务器立即停止所有供应商工作。

## 展示与产品提示

展示气温、体感温度、风速、天气描述，以及对应预报时刻前一小时的累计降水。降水不是瞬时雨量，也不是降雨概率。仅按来源字段生成固定提示：

- WMO 95/96/99：雷暴信号，出发前核对当地官方天气。
- 小时累计降水大于 0：留意户外及步行安排。
- 风速不低于 40 km/h：留意户外安排。
- 体感温度不低于 35°C：可考虑减少户外暴露。

这些是首版产品规则，不是官方预警等级或安全保证；未触发阈值也不等于没有风险。不会据此宣布某景点开放、关闭或必然适宜游玩。

改选方案、重新生成草案、修改条件或父规划请求进行中时，旧天气组件重置/卸载。查询失败后可重试，不保留旧数据冒充刷新成功。天气报告独立展示，不改推荐、手选方案、时间线、方案哈希、预算或保存内容。保存重开需主动重新查询天气，不会自动刷新或静默替换路线。
