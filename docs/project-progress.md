## 1. 项目目标与当前阶段

本项目面向真实城市出行规划场景：用户用自然语言描述起终点、到达时间和出行偏好，Agent 负责补齐必要信息，调用真实天气、地点与路线服务，比较多种交通方式，解释推荐依据，并支持路线切换、地图展示、行程保存和历史管理。

项目已经从“封装若干 MCP 工具的演示”推进为具有完整交互闭环的全栈应用。目前重点不再是增加孤立工具，而是提升复杂行程能力、数据实时性和工程化程度。

2026-10-22 地点搜索已从“Nominatim 主查、高德兜底”切为直接使用高德 POI 2.0；起终点使用同一提供方按顺序解析。前端地图已改为高德 JS API 2.0，旧存 WGS84 路线转换后绘制，真实底图已由用户确认。当前行程已独立管理并在电脑分栏/手机标签工作区展示，聊天不再重复放置完整路线卡片。单层出行偏好与独立限制表单已接入推荐链路。旧会话来源字段仍可读取；天气迁移、历史版本管理及其他 V2 能力仍待实现。

## 2. 当前系统架构

```text
React + TypeScript + Vite 前端
        │ HTTP / NDJSON 流式响应
        ▼
FastAPI API 层
        │
        ▼
AgentRuntime
├── LangChain create_agent / LangGraph
├── SQLite checkpoint（Graph 状态、审批恢复）
├── SQLite conversations（产品会话历史）
└── Qwen 模型接口
        │ MCP
        ├── Weather MCP    → Open-Meteo
        ├── Place MCP      → 高德 POI 搜索
        ├── Route MCP      → 高德地图路线服务
        ├── Planning MCP   → 多方式并行比较与确定性评分
        └── Itinerary MCP  → 本地 JSONL 行程存储
```

后端采用 `Domain → Service → MCP → Agent → API` 分层：

1. **Domain** 定义结构化输入、路线、候选方案和行程模型。
2. **Service** 封装第三方 API、坐标转换、路线解析与业务计算。
3. **MCP** 将稳定业务能力暴露为 Agent 可调用工具。
4. **Agent / Middleware** 负责意图理解、澄清、工具编排、状态控制与安全边界。
5. **API** 提供普通响应、流式响应、会话与行程管理接口。
6. **Frontend** 展示对话、结构化卡片、地图、审批和历史数据。

## 3. 已实现功能

### 3.1 Agent 与工具编排

- ✅ 基于 LangChain/LangGraph 构建 Agent，并通过 MCP 连接业务工具。
- ✅ 当前提供 9 个 MCP 工具：
  - `query_current_weather`
  - `search_places`
  - `resolve_route_endpoints`
  - `plan_driving_route`
  - `plan_walking_route`
  - `plan_transit_route`
  - `recommend_travel_plan`
  - `save_itinerary`
  - `list_itineraries`
- ✅ 对缺失城市、起点、终点和未来时间等必要信息进行澄清；可选偏好不会阻断基本规划。
- ✅ 通过系统提示、领域模型和展示层约束，避免把缺失费用解释为免费、把静态路线解释为实时路线等无依据结论。

### 3.2 真实数据与基础路线能力

- ✅ 查询城市当前天气，并转换为统一天气结构。
- ✅ 搜索地点并解析路线起终点。
- ✅ 获取驾车路线，包括交通态势下的预计耗时、收费信息和导航步骤。
- ✅ 获取步行路线和路径几何信息。
- ✅ 获取公共交通路线，解析地铁/公交/校巴等交通段、步行段、换乘次数和多个候选方案。
- ✅ 后端统一输出抽样的 WGS84 路线几何；前端高德地图组件通过官方坐标转换接口转为 GCJ-02 后绘制，兼容旧存路线。

### 3.3 综合规划、偏好与到达时间

- ✅ `recommend_travel_plan` 内部并行查询天气、驾车、步行和公共交通，减少串行等待。
- ✅ 根据耗时、费用、步行距离、换乘次数、天气和用户偏好执行确定性评分，而不是让模型凭文字自由决定排序。
- ✅ 支持均衡、速度、省钱、少步行、少换乘等出行偏好。
- ✅ 将驾车、步行和每条公共交通路线拍平成统一的“可执行行程候选”；用户一次点击即可切换完整方案，卡片、地图和保存对象同步更新。
- ✅ 交通方式仅作为方案属性和前端筛选条件，不再要求用户先选方式、再选公共交通子路线。
- ✅ 支持“几点前到达”等到达约束，计算建议出发时间并提示时间风险。
- ✅ 单个第三方服务失败时可降级返回仍然可用的方案，并明确数据缺口。

### 3.4 上下文感知与多轮重规划

- ✅ 通过 `thread_id` 和 LangGraph checkpoint 保留多轮状态。
- ✅ 保存最近一次结构化规划快照，而不是只依赖模型回忆上一轮自然语言。
- ✅ 在快照有效期内，用户修改普通偏好时直接对已有候选方案重新评分，不重复请求外部 API。
- ✅ 快照过期或修改公共交通策略时，Middleware 构造确定性的重新规划工具调用，刷新真实路线数据。
- ✅ 当实时刷新失败时，可回退到旧快照并在结果中标注数据可能过期。

### 3.5 结构化结果卡片与地图

- ✅ 后端将工具结果转换为稳定的 `PlanningResultCard`，通过 NDJSON 流式事件发送到前端。
- ✅ 前端同时展示流式 Markdown 回答和结构化规划卡片。
- ✅ 结果卡片展示统一方案列表及耗时、费用、步行、换乘、最快/最省等标签，并支持按交通方式筛选。
- ✅ 点击任意可执行方案后，当前选择、推荐说明、地图路径和待保存摘要联动更新。
- ✅ 驾车、步行和公共交通均支持路线地图；公共交通支持解析嵌套交通段几何。
- ✅ 地图的层级和容器样式已经处理，避免覆盖对话输入区域。

### 3.6 行程保存与人工审批

- ✅ 只有用户明确要求保存时才触发行程写入。
- ✅ `ItinerarySaveGroundingMiddleware` 将保存内容绑定到已经生成且被用户选中的可信路线快照，避免模型编造保存数据。
- ✅ `HumanInTheLoopMiddleware` 在有副作用的写入前中断 Graph，前端展示批准/拒绝操作。
- ✅ 用户批准后调用 `save_itinerary`，拒绝则不写入；服务重启后仍可从 checkpoint 恢复待审批状态。
- ✅ 保存成功后，Agent 返回成功提示，并告知可在“已保存行程”区域查看。
- ✅ 支持通过 Agent 或 REST API 查询已保存行程；前端可折叠展示列表。
- ✅ 支持查看详情、重新规划和删除；删除前需要确认，文件更新采用安全替换方式。

## 4. 核心实现流程

### 4.1 首次综合规划

```text
用户请求
  ↓
TravelRequestClarificationMiddleware 检查必要信息
  ↓
模型识别任务并调用 resolve_route_endpoints
  ↓
地点服务返回标准化起终点
  ↓
模型调用 recommend_travel_plan
  ↓
Planning Service 内部并行执行
  ├── 当前天气
  ├── 驾车路线
  ├── 步行路线
  └── 公共交通候选
  ↓
应用硬约束 → 计算特征 → 按偏好评分 → 选出推荐方案
  ↓
生成结构化规划结果和路线快照
  ↓
模型生成解释 + API 发出结果卡片事件
  ↓
前端展示方案、候选路线和地图
```

这里的“并行执行”发生在复合规划工具内部，不是 LangGraph 连续产生四次模型循环。

### 4.2 用户修改偏好

```text
用户：改成更省钱 / 少步行 / 更快
  ↓
PreferenceReplanningMiddleware 读取上一轮结构化快照
  ├── 快照仍新鲜、无需新数据
  │     ↓
  │   replan_from_payload 本地重新评分
  │     ↓
  │   直接返回新卡片并结束本轮，不调用模型和第三方 API
  │
  └── 快照过期或公共交通策略发生变化
        ↓
      构造 recommend_travel_plan 工具调用
        ↓
      刷新路线 → 重新评分 → 返回新卡片
```

本地重排用于“同一批候选方案下权重改变”；只有候选集合可能发生变化时才刷新外部数据。

### 4.3 用户切换可执行行程方案

```text
用户点击任意完整方案卡片
  ↓
前端根据 plan_id 发送规范化选择消息
  ↓
Middleware 读取当前规划快照并确定性更新对应方式/公交候选
  ↓
API 重新生成统一 route_candidates 与 selected_plan_id
  ↓
返回新的结构化卡片
  ↓
前端同步更新卡片高亮、详情、RouteMap 和待保存摘要
```

驾车、步行和每条公共交通路线在界面上都是同一级的可执行方案。交通方式仅用于标记和筛选，保存行程时只以当前 `selected_plan_id` 对应的具体路线为准。对于未手动切换方案的初始结果，系统推荐方案就是默认当前方案，可直接进入保存审批。

### 4.4 保存行程

```text
用户点击保存或明确提出保存
  ↓
Grounding Middleware 从当前可信快照提取所选路线
  ↓
Agent 发起 save_itinerary
  ↓
HITL 中断，前端展示待批准操作
  ├── 拒绝：结束，不写入
  └── 批准：恢复 Graph 并调用 Itinerary MCP
              ↓
            写入本地 JSONL
              ↓
            Agent 返回保存成功提示
              ↓
            前端刷新“已保存行程”
```

### 4.5 会话恢复

- **LangGraph checkpoint**：保存消息、工具调用、规划状态和审批中断，服务于执行恢复。
- **Conversation SQLite**：保存用户可见的会话列表和消息，服务于产品历史界面。
- **Itinerary JSONL**：保存用户明确批准的行程，服务于查询、详情、重新规划和删除。

三类存储职责不同，不能用单一聊天记录替代结构化运行状态。

## 5. 当前已知边界与技术债

### 5.1 数据边界

- ⛔ 天气目前是城市级当前天气，不提供逐路线分钟级降雨、紫外线和精细天气风险。
- ⛔ 驾车可使用交通态势耗时；步行和公共交通仍主要是静态规划结果。
- ⛔ 暂无公共交通车辆实时位置、实时到站和稳定班次数据。
- ⛔ 公交费用为 `null` 时表示数据缺失，不能解释为免费。
- ⛔ 地图展示的是规划时刻的抽样路线快照，不是实时导航；高德底图与坐标转换依赖网络及独立 JS API 配置。用户已确认底图显示正常，方案选择实际点击与后端状态已验证，不能据此声称具备实时导航。
- ⛔ 行程目前保存在本地，不支持账号同步、多人共享、下单或票务预订。

### 5.2 当前实现中的待优化点

- 单层“本次出行偏好”与独立硬限制已实现，旧版策略字段仅作迁移输入及提供方提示；完整历史版本入口仍待实现。
- “地铁优先”等公共交通策略改变时，目前会刷新整个综合规划，天气、驾车和步行也会重复请求；后续应支持只刷新公共交通分支。
- 第三方服务的超时、配额与异常已有降级，但还缺少统一结构化日志和跨层 Trace。
- 前端主页面承担的状态较多，后续可按对话、规划卡片、行程和地图进一步拆分。

### P0：多目的地行程规划（核心产品增量，🟡 已完成方案设计）

目标：支持“从 A 出发，依次或智能安排经过 1–4 个地点，最后到 B”的复杂行程，而不只是单起点—单终点路线。

已经确定的产品范围：

- 输入起点、1–4 个中间点和终点。
- 每个地点可设置停留时间、时间窗和必须先后约束。
- 支持最终到达截止时间和全局出行偏好。
- 输出访问顺序、逐段路线、完整时间线、风险提示和多段地图。
- 用户修改地点、顺序、时间或偏好后执行确定性重规划。
- 保存前仍经过 HITL；保存结构升级为 `schema_version=2`、`itinerary_type=multi_stop`。

建议实施阶段：

1. **领域模型与接口**：定义多点请求、停留/时间窗、路线矩阵和多段结果。
2. **Mock 路线矩阵**：先用固定数据验证排序、时间推演和约束逻辑。
3. **确定性优化器**：最多 4 个中间点时枚举排列，先过滤硬约束，再按耗时、费用和偏好排序。
4. **接入真实路线**：复用地点解析和高德路线服务，批量构建点对点矩阵。
5. **Agent 接入**：由模型提取/确认结构化意图，具体排序交给确定性优化器。
6. **前端交互**：地点编辑、时间线、多段路线卡片与地图联动。
7. **保存与评估**：升级行程存储，增加约束满足率、最优性和异常场景测试。

预计可复用现有地点解析、路线服务、偏好评分、地图、HITL、存储和 API 基础约 55%–65%；新增工作主要是多点领域模型、路线矩阵、组合优化、时间模拟和多段 UI。
