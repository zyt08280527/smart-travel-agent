# 目的地推荐的连续对话

2026-10-25：用户确认先补连续对话，景点扩库安排在上线之后。当前仍只比较现有三个深圳馆区，不增加景点、兴趣或同行者筛选。

## 已实现

从“帮我选目的地”提交并获得候选后，可直接说：

- “预算改成50元”“取消预算限制”。
- “只有两小时”“往返总时长改成三个小时”。
- “停留改成60分钟”，支持与预算、总时长在同一条消息修改。
- “不能驾车”“改成少步行”“最多步行一公里”“最多换乘两次”，或显式取消对应上限。
- “换一个目的地”：排除当前第一推荐；已经选定并生成路线后，明确说“换一个目的地”则排除所选馆区。
- “取消排除”“恢复全部候选”，明确恢复被排除的馆区；不会自动扩大范围。
- “取消修改”：丢弃尚未应用的修改，继续使用上一次条件与结果。

保留未修改的起点、日期、预算、停留、出行偏好、累计限制、开放要求和天气策略；重新推荐仍走原事实与完整路线服务，不把前端指标当成已计算事实。改变预算等支持项后同步右侧候选与弹窗字段，不自动保存正式行程。

## 澄清与失败保护

原停留120分钟时说“只有两小时”会产生冲突：保留待确认的总时长120分钟，追问停留；用户再说“停留改成60分钟”后合并并重新计算，不自动缩短停留。裸“60分钟”或“好”不足以区分总时长与停留，继续澄清。待确认状态可在当前标签页刷新后恢复。

冲突、区间/模糊表达、矛盾数值、范围外参数，以及一条消息混入尚不支持的条件时，不部分应用已识别字段。右侧明确标注仍为旧结果，暂停采用旧候选，用户可以补充、重试或取消修改。网络失败不覆盖上一次有效条件与结果。换候选逐步累积明确排除，候选耗尽显示为空，不自动恢复、放宽预算或扩库。

旧版本缓存没有完整推荐条件时，不从候选反推预算或可用时长，提示重新打开弹窗确认一次。新建对话/切换历史不会串用旧推荐上下文。

## 接口与状态

新增 `POST /api/discovery/refine`：输入原 `DiscoveryRequest`、用户消息、候选ID及可选的已选馆区、待确认部分修改；返回 `updated/clarification/not_applicable/cancelled`、有效请求、待确认修改、结果和固定说明。待确认修改仅序列化真正提供的字段，区分未修改与显式清除，避免默认null覆盖原条件。

`DiscoveryRequest.excluded_attraction_ids` 最多三个，后端只接受现有启用馆区。排除在路线查询前执行，剩余馆区仍按原时间、预算、步行、换乘和天气限制核算。推荐/澄清不创建多站点草案或保存记录；用户选定后才走完整规划与显式确认保存。

本阶段采用保守的确定性中文条件解析，不新增模型调用或MCP工具，不宣称支持任意自然语言。更换起点、日期、天气策略仍可用弹窗；单程探索、任意增删景点、自由兴趣推荐未在本轮扩展。普通新路线问题继续原Agent链路；生成路线后普通预算/偏好修改继续当前行程链路，明确要求重新推荐目的地才回到推荐阶段。

当前新推荐已接服务端会话历史，同时保留标签页缓存。原推荐请求、候选、待确认部分修改、当前阶段及已选草案/方案与会话绑定；从历史列表重开不依赖本地缓存，可以继续澄清。推荐说明和对应状态原子写入现有会话库的新表，不覆盖旧消息；版本不符或正在审批时拒绝旧写入。读取历史不会重新查询外部路线。

推荐/修改携带线程ID和预期版本；后端以该会话已保存的条件为准，忽略浏览器提交的旧基线。选择目的地走会话专用choose接口，后端读取该会话可信候选后重算完整路线并保存草案引用和说明，不自动保存正式行程。手选完整方案/分段后的新草案引用可同步到历史；失败显示提示并允许重试，不伪装成已经同步。历史恢复优先使用服务端手选ID，不能被草案默认推荐覆盖；后续普通聊天产生了更新路线时，不让旧推荐阶段遮挡新路线。

新表与消息在同一SQLite事务写入，删除会话级联清理推荐状态。既有普通会话兼容为空状态；之前仅在旧版浏览器缓存的推荐不被伪造成服务器记录，需要重新确认一次。鉴权/账号隔离与正式部署仍按原计划后置，不把本地历史持久化称为完整多用户上线能力。
