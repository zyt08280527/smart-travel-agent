## 1. 产品定位与首个场景

产品定位扩展为：**帮助城市用户从“决定去哪、何时出发、怎么走”，到“执行途中变化后怎么办”完成一次可执行的出行决策**。用户不局限于通勤或办事，但 V2 首版仍以有明确目的地的同城行程为切入点，避免同时扩张目的地内容、交通数据和交易能力。

| 用户任务 | 典型提问 | 产品重点 | 优先级 |
| --- | --- | --- | --- |
| 准时赴约或通勤 | “明早 9 点前到公司，几点出门更稳妥？” | 到达约束、出发提醒、天气/路线变化 | V2 核心 |
| 多地点办事或活动 | “先办事再取快递，下午 2 点前到学校” | 多站点时间线、停留时间、分段路线 | V2 核心 |
| 周末休闲或家庭出行 | “周六去公园和博物馆，避开下雨和长距离步行” | 同一套多站点规划，加天气和体力偏好 | V2 核心场景扩展 |
| 暂无明确目的地 | “周末有半天，想找适合带父母去的地方” | 从有限、核验过的景点库生成候选，再进入行程规划 | V2-3 限定范围试点 |

这是一条按**任务**而非年龄或职业划分的用户线：已有目的地时执行规划与守护；目的地尚未确定时，只从经人工核验的深圳景点范围内生成可解释的地点候选。不能让模型凭空推荐“正在营业”或“适合所有人”的场所。

首个端到端场景：

> “周六 9:00 从深圳大学粤海校区出发，先到医院，至少停留 40 分钟，再去取快递，13:00 前到丽湖校区；尽量少步行。如果下雨或可能迟到，出发前提醒我。”

完成后的产品应让用户看到：确认过的地点和时间、每段可执行路线、整段时间线与约束风险、选定并保存的行程，以及出发前重新检查后的提醒或替代方案。用户始终能区分“查询时估计”“出发时段预报”和“已经更新的路线”；无数据时不编造费用、班次或准点保证。

产品主流程：

```text
自然语言/表单输入 → 澄清歧义并确认地点 → 生成整段行程
→ 查看时间线/每段路线/地图 → 调整地点、时间或偏好
→ 明确确认并保存 → 出发前自动检查 → 保持原方案或建议重规划
→ 用户采纳/忽略 → 完成或取消
```

当前已有单段规划、多方式候选、地图、偏好重排、HITL 保存、会话历史和出发时段天气查询。V2 不以“再增加几个 MCP 工具”为目标。

### 非目标

- 首版不做实时公交车辆位置、实时到站、导航跟踪、买票/打车下单或价格保证。
- V2 的目的地探索限定深圳约 20–30 个经过核验的景点；不做无限制的全网种草、商家评价聚合或营业状态保证。
- 不自动抓取、复制或储存小红书笔记全文；未取得授权前，不把小红书笔记检索/总结作为上线依赖。
- 不承诺未来时段的精确路况；查询时路线耗时用于估算，必须显示时间依据与数据时间。
- 不做全国无限站点旅行商问题；首版限定**同城、固定访问顺序、1–3 个中间点**。允许重排顺序放在后续子阶段。
- Java Agent 任务平台保持独立项目；V2 先沿用 Python 后端，不为技术栈展示而拆微服务。

## 3. 关键页面与交互

1. **创建行程**：自然语言为入口，同时提供可编辑的起点、终点、中间点、停留时长、最早/最晚到达、出行偏好和“是否守护”。地点同名、时间缺失或约束冲突时只追问必要字段。
2. **行程结果**：顶部显示总预计耗时、预计到达时间与风险；中部按时间顺序显示每一站和每一段交通方案；地图绘制全部分段并高亮当前段。每段显示交通方式、耗时、步行、换乘、已知费用、数据来源及刷新时间。
3. **修改与比较**：用户修改一站的停留时间或某段交通方式后，重新计算后续时间线。界面保留前后版本差异；原方案在用户确认之前不被覆盖。
4. **确认和保存**：保存对象必须是用户当前选中的完整行程版本。沿用现有可信快照与 HITL 边界，但界面应将“确认保存”和 Graph 审批合并为一个可理解的动作，避免同一写入让用户无故确认两次。
5. **我的行程**：分“即将出发 / 已完成 / 已取消”，可查看、编辑、关闭提醒和重新规划；手机宽度下时间线与地图仍可操作。
6. **守护提醒**：通知说明触发原因、原方案与新估计的差异、检查时间和来源，并提供“查看替代方案 / 保持原方案 / 关闭提醒”。通知不得直接替用户改动已确认路线。
7. **景点信息卡**：地点确认后若匹配到景点，按需展开景点简介、建议游览时长（明确标注为建议）、是否需提前预约、预约方式、官方入口、参考票价/票种、开放信息。每一项动态事实单独显示来源和核验时间；未知就显示“待核实”，不默认“免费/免预约/营业中”。点击官方入口可跳转，不代用户下单。
8. **去哪玩**：用户提供可用时间、出发位置、预算、同行者与步行/天气偏好；页面展示 3 个不同类型的候选及推荐理由、预计路程、预约风险和缺失信息。用户选定后进入既有地点确认与行程规划流程，而不是另起一套不可保存的聊天结果。

- **电脑端布局**：左侧对话，右侧“当前行程”；工作区统一包含候选路线、地图、本次出行偏好、出行限制、系统推荐、当前选择及保存入口。聊天输入框保持在对话下方，地图在自己的布局区域内显示。
- **手机端布局**：提供“对话 / 当前行程”两个标签，共用同一份当前行程状态，切换标签不丢失草稿或选择。
- **对话职责**：说明变化和原因，例如“已切换地铁方案，预计多用 12 分钟、费用减少 8 元”（数字必须来自真实新旧方案比较）；附“查看当前行程”入口。聊天保留决策过程，不重复插入整套候选与地图。
- **工作区职责**：仅展示当前有效草案或用户选定版本。自然语言修改、偏好按钮与候选点击走同一状态更新链路；推荐标识、选中标识、路线步骤、地图及待保存摘要必须来自同一版本和 `plan_id`。
- **更新过程**：计算期间标明正在更新，成功后一次性应用完整结果；失败时保留上一个可用版本并说明失败，不让地图更新而保存摘要仍指向旧方案。保存只接受当前有效、已选定的版本。
- **历史方案**：通过工作区的“方案版本”入口按需查看。查看旧版是只读操作，只有点击“采用此方案”才切换当前草案；快照过期状态仍需展示。已保存的行程不因查看或修改草案而被覆盖。
- **重新打开会话**：从该会话恢复当前行程；切换或新建会话时不能沿用另一会话的路线。工作区状态不依赖结果卡片在消息数组中的位置，历史消息和当前业务选择分别维护。

验收：首次规划后只出现一个当前行程工作区；连续切换三种方式、自然语言修改和偏好调整后，工作区始终显示同一有效版本；聊天只记录变化；刷新/重新打开、会话切换、移动端标签切换、旧版查看及采用、保存与更新失败均有测试覆盖。

### 3.2 一组偏好、独立限制、明确选择（2026-10-22 已实现并通过本地验证）

取消“通用偏好 + 高级设置中的公共交通偏好”两层结构，只提供一组单选的**本次出行偏好**：

| 偏好 | 对整个行程推荐的作用 |
| --- | --- |
| 综合推荐 | 在满足限制的具体候选间综合比较时间、已知费用、步行、换乘和天气适配 |
| 时间优先 | 提高耗时的排序优先级 |
| 省钱优先 | 提高已知费用的排序优先级；未知费用不按零计入 |
| 少步行 | 提高总步行量的排序优先级 |
| 少换乘 | 提高换乘次数的排序优先级 |
| 地铁优先 | 优先推荐满足限制且包含地铁段的具体公共交通路线；无合适地铁路线时回退到其他可行路线并解释原因 |

**出行限制**另设区域：不能驾车、最大步行距离、最大换乘次数、到达截止时间等是硬条件，先于偏好处理。“少步行”是优化目标，“最多步行 800 米”是硬限制；“地铁优先”不能覆盖到达时间或步行上限。偏好区不再另列公共交通内部的“综合推荐 / 少换乘 / 少步行”。

**具体路线选择**是独立动作：点击某条候选表示“采用这条路线”，不修改偏好。界面分别标注“系统推荐”和“当前选择”；用户可采用非首选的可行路线。交通方式快捷按钮如保留，明确表示选用该方式的首个可行候选；纯筛选操作必须明确标注，不能让用户误以为已选择。地图和保存对象跟随当前选择，而非始终跟随系统推荐。

统一流程：**验证出行限制 → 按一项出行偏好推荐具体路线 → 用户选用路线 → 保存当前选择**。修改偏好生成新的草案结果并解释推荐变化；旧已保存版本保留。若原手动选择因新限制而不可用，说明原因并要求重新选择，不能静默保存旧选择。

实现需同步调整前端控件、自然语言解析、领域字段、排序逻辑、流式事件、地图选择与保存读取；只改按钮名称不算完成。现有 `priority` 与 `transit_strategy` 可以作为迁移输入，但旧版“地铁优先仅调整公交内部”的行为不得冒充新语义，旧会话需有明确兼容规则。

验收：全页面仅一组上述偏好；在存在满足限制的地铁候选时，地铁优先的系统推荐必须是对应具体地铁路线，即使驾车更快；无地铁候选时给出回退原因；硬限制始终优先；手动选择非推荐路线后，偏好保持原值，当前选择、地图和保存摘要一致。

本次落地：前端仅展示六项单选偏好；独立折叠表单设置驾车条件、步行上限、换乘上限，到达目标仍通过对话设置。`priority` 是唯一主偏好，`transit_strategy` 仅由其派生为提供方查询提示。旧数据主偏好为 balanced 且存在具体旧策略时提升旧策略；明确的非 balanced 主偏好优先，切回 balanced 时清除旧策略。历史快照不会因前端渲染自动重算，新一次调整后按新规则计算。推荐地铁候选索引与手动选用索引分离，流式卡片、地图与保存分别读取对应状态。硬限制与到达时间在公共交通候选选线前生效，无可行地铁时给出回退提示。已覆盖更快驾车与地铁、硬限制排除地铁、无地铁、到达时间、旧字段迁移，以及手动选公交但仍推荐地铁且保存公交的测试。浏览器只读验收桌面/手机六项偏好与布局，无横向溢出或运行错误；未在本轮调用真实模型或重新请求路线，不代表线上服务验收。完整历史版本入口及采用旧版仍待实现。

## 4. 领域模型与状态边界

拟新增的持久化实体：

| 实体 | 核心字段 | 用途 |
| --- | --- | --- |
| `User` | `id`、登录标识、通知同意状态 | 所有行程和会话的归属边界 |
| `Trip` | `id`、`owner_id`、`schema_version=2`、状态、时区、全局偏好、出发/到达约束、当前版本号 | 一段完整行程，不等于一轮聊天 |
| `TripStop` | 顺序、地点名/坐标/提供方 ID、停留分钟、时间窗、是否允许重排 | 需要访问的地点 |
| `TripLeg` | 起终站、交通方式、所选 `plan_id`、路线摘要、几何、数据依据/时间、可用性 | 两站之间的一段可执行路线 |
| `TripRevision` | 版本号、输入快照、计算结果、创建原因与时间 | 修改、守护和回滚时可比较旧方案 |
| `WatchJob` | 行程版本、下次检查时间、状态、租约、尝试次数 | 持久化的出发前检查任务 |
| `Alert` | 事件键、触发条件、证据摘要、发送状态、时间 | 去重、追踪与用户查看 |
| `AttractionProfile` | POI ID、规范名称、类别、位置、室内/室外标签、适宜停留时长范围、启用状态 | 试点景点候选池；与路线地点实体关联 |
| `AttractionFact` | 景点 ID、事实类型和值、来源 URL、核验时间、适用日期/人群、失效时间或状态 | 预约、价格、开放信息的可追溯记录；允许 `unknown` |

拟议行程状态：`DRAFT → CONFIRMED → WATCHING → ACTIVE → COMPLETED`；`DRAFT/CONFIRMED/WATCHING/ACTIVE` 可以取消。`WATCHING` 表示已同意并启用检查，不表示正在实时追踪。行程更新使用版本号并发控制；后台检查只针对最新的已确认版本。用户撤销通知同意、取消行程或出发时间已过时，停止后续守护任务。

兼容原则：现有 `SavedItinerary` 是单段 JSONL 记录，缺少用户归属和多段字段。迁移时保留原文件备份，将其作为 v1 单段行程导入或提供只读兼容；不能把旧记录凭空转换成多段行程。LangGraph checkpoint 仍存 Agent 过程态，产品数据库存用户确认的业务状态，二者不互相代替。

## 5. 规划与守护的确定性规则

### 5.1 多段规划

1. 模型只提取意图并标记不确定字段；地点候选由用户确认。结构化请求通过校验后进入规划服务，不由模型自由编造路线。
2. 先按用户给定顺序构造相邻站点的路线段，复用现有地点解析、驾车/步行/公共交通服务和天气服务。每段候选附 `source`、`fetched_at`、`duration_basis`、`cost_known`、`limitations`。
3. 将出发时刻、路线耗时、停留时间和地点时间窗依次向前推演。硬约束不满足则排除该组合，返回“第几站、预计差几分钟、原因是什么”，不得给出伪可行计划。
4. 首版允许步行与公共交通在各段之间组合；驾车一旦选择，默认全程保持有车可用。**不能让私家车在上一站停下后，下一段凭空重新出现**。停车换乘需以后单独建模。
5. 对可行组合按总时间、已知费用、步行、换乘及偏好确定性排序。费用未知不得按 0 元参与“最省钱”结论。限制组合数量和外部调用预算，优先做短列表与剪枝，不对全部点对与全部方式无界请求。
6. 路线耗时标注“查询时估计”，不冒充未来实时路况。天气默认先查询高德的区域实况与按天预报；若用户指定出发小时、产品仍需小时级降雨/体感判断，则只为该字段保留现有小时级天气提供方，并在结果中分别标注来源，不能把高德按天预报伪装为指定小时预报。公交/地铁班次若数据不足，标注需在出行前确认。

### 5.2 行程守护

- 用户明确开启后，调度器在出发前的可配置检查窗口运行；默认规则先以“出发前约 2 小时、30 分钟”作为**待实验参数**，不是已经验证的最佳频率。
- 对已确认行程的当前版本重新获取可用路线与时段天气，比较预计到达时间、缓冲余量和方案可用性。仅当变化超过配置阈值或硬约束由可行变不可行，才生成候选提醒；提醒阈值需要在测试中校准。
- 只复用仍新鲜、适用于相同站点与时段的数据。查询失败时记录“本次未能验证”，延后有限次数重试；不能把服务错误解释为交通异常。
- 事件键由 `trip_id + revision + alert_type + check_window` 构成，在数据库中唯一约束，避免 worker 重启或重试造成重复通知。通知失败可重试，发送成功有审计记录。
- 首版外部通知拟采用用户验证邮箱且明确同意后的邮件，辅以站内消息；浏览器推送可后置。未同意者只在站内查看，不做后台外发。

### 5.3 景点信息与开放式推荐

1. **先确认实体，再读取内容**：优先通过高德 POI ID、类型和城市匹配 `AttractionProfile`，同名馆区由用户确认。仅凭名称含“公园/博物馆”不能判定预约规则。
2. **事实来源分层**：预约/票价/开放时间优先来自景点官方或政府页面；地图 POI 只用于地点、分类及可能存在的营业信息。高德 POI 的 `cost` 是人均消费，**不得当作门票价格**。每条动态事实保留原链、核验日期和适用范围；过期或冲突时降级为“待核实”，附官方入口。
3. **不做虚假可订承诺**：字段区分 `reservation=required/not_required/unknown`、`ticket_price=free/range/unknown`，但“预约要求已核实”也不代表用户所选日期有余票。只提供官方预约/购票入口，不保存身份证件或代填支付信息。
4. **有限库的去哪玩**：先从深圳约 20–30 个经核验的候选景点中召回；用城市、日期、开放信息、预约提前量、预算上限、步行上限、同行者等做硬约束过滤。事实未知时不能当作硬满足，用户明确要求“确保可预约/开放”则只保留已核实候选。
5. **先筛选后算路线**：对剩余少量候选计算从用户出发点的路线时长、天气适配、时间预算和偏好得分，再做类别/区域多样性控制，展示前 3 个及每项取舍。模型负责提取需求和引用事实解释，不能新增不在候选库的地点。
6. **与行程闭环衔接**：选中推荐景点后转入现有地点确认、单段/多段路线规划、保存和守护流程。信息卡可指出“建议停留 60–90 分钟”，但最终停留时间由用户确认并进入约束计算。

**社区攻略接入研究（不进入 V2 上线关键路径）**：先验证是否能通过平台授权或合规搜索服务获得可展示的原帖链接与许可范围。可先提供“查看原帖”跳转；用户主动提供且有权使用的文本，如访问和平台条款允许，可做不复制全文的短摘要与观点归纳，并标注为个人体验，不能据此证明票价、预约或营业事实。未取得稳定授权前，不做自动登录、非公开接口、批量抓取或长期储存笔记全文。

## 6. API 与技术分层草案

保留现有 `React/TypeScript → FastAPI → Agent/MCP → Service/Provider` 主线，增加产品业务层与异步检查层。**外部地图与位置能力以高德为首选提供方**；这不等于所有出行事实都能由高德给出。

```text
Web UI ── Chat / Trip API ── TripService ── Relational DB
                    │              │
                    │              ├── PlanningService → 地图/天气 Provider Adapter
                    │              └── Revision / Alert Service
                    └── Agent → MCP（理解、澄清、调用规划能力、解释）

Scheduler/Worker ── 领取到期 WatchJob ── 刷新与比较 ── Alert ── 邮件/站内通知
```

拟新增端点（名称在实现时可调整）：`POST /api/v2/trips/plan`、`POST /api/v2/trips`、`GET /api/v2/trips`、`GET /api/v2/trips/{id}`、`PATCH /api/v2/trips/{id}`、`POST /api/v2/trips/{id}/confirm`、`POST /api/v2/trips/{id}/replan`、`POST /api/v2/trips/{id}/watch`、`DELETE /api/v2/trips/{id}/watch`、`GET /api/v2/alerts`，以及 `GET /api/v2/attractions/{id}`、`POST /api/v2/attractions/recommend`。所有读写均从认证上下文确定 `owner_id`，不能信任客户端传来的用户 ID。现有 `/api/chat` 与单段 API 在迁移期保留，避免一次性破坏当前功能。

首版可采用单实例 Web/API + 关系型数据库 + 独立 worker；不强制引入 Redis。定时任务需持久化、可租约领取与幂等执行，不能只靠进程内 `asyncio.create_task`。若后续多实例或高并发再根据测量结果引入消息队列/缓存。

### 6.1 高德优先的外部能力分工

| 能力 | V2 首选 | 接入边界 |
| --- | --- | --- |
| 地点搜索、景点候选、地点详情与同名消歧 | 高德 Web 服务 POI 2.0 | 使用 POI ID、类别、坐标、行政区等；可选营业字段只作线索，节假日与临时闭馆仍需官方核验。 |
| 驾车、步行、公共交通路线及部分费用/路况信息 | 沿用并扩展现有高德 Web 服务路线适配器 | 路线结果是查询时估计；公交费用、班次或事件字段缺失时不补造。多站点由本项目逐段调用并计算时间线，不声称高德直接完成整段行程优化。 |
| 地图底图、站点标记和路线轨迹 | 地图组件已接入高德 JS API 2.0，多段行程地图仍待实现 | 现有 API 与旧存路线保留 WGS84；前端用官方 `convertFrom` 每批最多 40 点转换为 GCJ-02，再绘制。真实底图显示已由用户确认，方案选择状态已做独立浏览器验证。 |
| 区域天气实况、今日及未来按天预报 | 高德天气 Web 服务 | 按 `adcode` 查询，保留发布时间；不把按天预报当作“明早 8 点是否下雨”。 |
| 指定出发小时的天气判断 | 现有小时级天气服务作为**明确的补充** | 仅在需要且许可/配额适合公开服务时调用；否则显示“小时级天气暂不可用”，守护规则不基于缺失数据给出确定性天气告警。 |
| 景点预约规则、票价、官方购票链接 | 景点官方或政府来源，经核验入库 | 高德 POI 的 `cost` 是人均消费，不是门票；无可靠来源则显示“待核实”。 |
| 社区游记/攻略 | 暂不接入自动检索 | 高德位置 API 不能替代社区内容授权。 |

迁移进度：保持现有高德路线能力不动；**地点搜索已于 2026-10-22 改为高德 POI；前端地图组件已迁至高德 JS API，通过本地自动化测试，用户已配置 Key 并确认底图显示正常**。方案切换的实际点击与后端状态已做独立浏览器验证；详见进度文档的联调记录。后续接入高德天气实况/按天预报，与原有小时级能力逐字段比较后再切流。天气迁移仍是规划，可在工作区与偏好整改之后推进。

密钥分离：后端高德 Web 服务 Key 仅在服务器使用；前端地图使用单独的 Web 端 JS API Key、受控域名及官方要求的安全配置，安全密钥不得明文写入仓库。高德配额、商用授权、展示归属及服务条款在上线前按实际账号与域名复核。

## 7. 测试与产品度量

**确定性测试**：固定路线矩阵覆盖多站点、时间窗刚好满足/超时、用户先后顺序、未知费用、公交不可用、驾车连续性和时区跨日。对固定输入，约束判定及路线顺序必须可复现；硬约束违规为 0。

**外部服务契约测试**：用录制/模拟响应检验高德地点、路线、地图坐标与天气字段，以及补充天气源的小时级字段；至少覆盖单个服务超时、配额耗尽、费用缺失、路线快照过期、不同坐标系叠加和天气粒度不足。不得以 mock 成功冒充真实服务上线通过。

**端到端测试**：从输入场景到地图、多段选择、确认保存、重新打开、修改、守护触发、邮件/站内通知、取消守护，至少覆盖一条正常链路和一条失败降级链路。验证重启后任务恢复、通知不重复、跨账号无法读取。

**工作区与统一偏好验收**：先在现有单段链路覆盖第 3.1、3.2 节场景，再复用于多站点。测试区分系统推荐、当前选择和只读历史版本，覆盖连续快速切换时旧异步结果不得覆盖新状态，以及更新失败时当前路线与保存对象保持一致。增加地铁优先与驾车更快、地铁违反硬限制、无地铁候选、未知费用及旧会话迁移的固定样本。

**景点评估**：维护覆盖同名馆区、预约规则变化、免费但需预约、分时票价、闭馆、数据缺失和降雨的固定样本。要求测试样本中的预约/价格断言均能追溯来源，虚构确定性预约或票价结论为 0；候选中明确违反硬约束的比例为 0。线上展示字段覆盖率、用户查看官方入口率和建议采纳率需记录样本量，不能把离线用例通过率当作线上效果。

**产品指标**：规划完成率、地点澄清率、保存率、保存后修改率、景点推荐采纳率、官方预约入口点击率、守护提醒打开/采纳率、用户报告的错误提醒率。工程指标：各外部 API 成功率与耗时、每次规划调用数、模型 Token/费用、事实核验过期比例、后台检查延迟、重复通知数。上线前定义埋点口径；所有结果按样本量、环境和真实/模拟数据分开报告，不预填成绩。

## 8. 服务器上线门槛

1. **部署**：确定服务器地区、域名与预算；使用 Docker Compose 部署前端静态资源、API、数据库和 worker，反向代理提供 HTTPS。配置与密钥经环境/密钥管理注入，不能进入镜像或 Git。预览环境先走完整部署和回滚演练。
2. **安全与隐私**：登录/会话鉴权、对象级授权、请求限流、输入长度限制、日志脱敏；用户可查看和删除自己的数据。公开 Demo 不允许任何人凭 UUID 访问或删除其他人的行程/会话。个人位置和行程设置保留期限，通知必须可关闭。
3. **数据可靠性**：数据库迁移、持久卷/托管数据库、自动备份和一次真实恢复演练；checkpoint 与业务数据的备份策略分别记录。部署重启不能丢已确认行程和待守护任务。
4. **可观测性**：请求与行程版本关联 ID、Provider 耗时/失败分类、模型费用与配额监控、worker 积压和告警；健康检查区分进程存活与关键依赖可用。
5. **供应商检查**：V2 拟以高德承接地点、路线、地图及基础天气；上线前用真实账号和域名验证 Web 服务与 JS API 各自的 Key、安全配置、POI/路线/天气配额、使用许可、展示归属和费用。当前公共 Nominatim/OSM 底图仅作为迁移前实现，不作为公开产品默认依赖。小时级天气如继续使用 Open-Meteo，须另核对公开使用范围、许可与配额；其服务故障不可被解释为无雨。景点官方信息的使用许可与复核机制也需确认。社区攻略未获授权时不接入自动检索。
6. **发布门槛**：CI 中后端、前端、数据迁移和关键端到端测试通过；完成真实供应商冒烟、移动端检查、备份恢复、密钥检查、跨用户安全测试与回滚演练。然后邀请少量真实用户试用，再逐步开放。

## 9. 实施前需要确认的产品决策

以下为待确认项，不阻挡编写本设计，但会影响实现和采购：

- 首批目标城市是否只选深圳？建议先单城，降低地点、天气、公交和测试矩阵复杂度。
- 公开测试的服务器地区、每月预算、域名和是否允许仅邀请制试用？建议先邀请制上线，再开放注册。
- 邮件通知是否可接受？若只做站内提醒，用户不打开网站就收不到“出发前提醒”，产品承诺需相应收窄。
- 地图、地点、路线和基础天气已确定**高德优先**；仍需用真实调用量预估其配额/费用，并确认 JS API Key 与 Web 服务 Key 的实际开通权限。
- 对“明早某个小时是否下雨”，是否继续保留独立小时级天气服务？建议保留为明确补充；若不能满足上线许可或预算，则下线该粒度的承诺而非用高德按天预报替代。
- 深圳试点景点首批清单、官方来源核验责任与复核频率如何确定？建议从博物馆、公园、室内展馆各选若干处，不声称覆盖全城。
- 社区攻略是只提供外链，还是在获得明确授权与稳定数据入口后再做摘要？默认只研究，不进入上线承诺。
