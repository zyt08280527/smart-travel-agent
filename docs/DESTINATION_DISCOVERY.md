# “去哪玩”往返试点

2026-10-23：用户要求暂停景点扩库，确认转入 V2-3 最小闭环。沿用现有深圳 3 个馆区/5 个 POI，没有新增景点。

## 已实现流程

当前入口为“帮我选目的地”弹窗，主界面始终保留左侧对话与右侧结果。用户搜索并显式点选深圳高德出发点，填写往返总可用分钟和确认游览停留时长；北京时间出发时刻可选，可设置交通与普通门票预算、累计步行/换乘限制、驾车条件及路线偏好。当前不提供兴趣/同行者筛选。

`POST /api/discovery/recommend` 只从现有启用馆区生成候选。先检查指定日期开放要求、已核验门票数值与复核期限，再对剩余馆区使用 `MultiStopPlanningService` 核算“出发点 → 馆区 → 原出发点”。总可用时间同时包含往返交通和游览，不把停留时长当作全程时长，也不压缩用户已确认的停留来凑可行结果。

馆区内路线沿用既有六项确定性偏好；馆区之间按往返预计耗时、馆区 ID 稳定排序。当前只有博物馆，不伪造类别多样性或宣称覆盖全市。结果含路线估计、步行/换乘、费用已知性、来源/查询时间、推荐理由、待核实风险与未入选原因。这里没有训练推荐模型，也没有自然语言需求提取或新的 MCP 工具。

提交后关闭弹窗，左侧依据服务返回的真实推荐原因与限制生成固定说明，不额外调用模型编造推荐；右侧展示目的地候选、介绍、预计往返总耗时、交通与停留、已知费用及限制。点击“规划去这里”或明确回复“去完整馆区名”后，重新调用完整多站点规划，右侧切换为所有往返分段、时间线/相对耗时、地图与确认保存；原 POI/城市/坐标、顺序、停留、预算和累计限制均保留。推荐接口不创建草案或保存记录，选择候选只生成草案，不自动保存，不复用筛选时快照作为最新路线。

未指定出发时间时，推荐请求允许 `departure_at=null`，不生成具体日期或返回截止；`max_elapsed_minutes` 在全组合排序前限制交通、等待与停留总耗时，不能只筛已返回的前三项。正式规划与分段修改继续校验该时长上限。只有明确启用按到达时刻的天气处理才要求填写时间，也可保持“不查询天气”。有时间时原截止校验仍保留。两个可选限制字段为空时均不改变旧方案 ID。

已完成候选和聊天说明保存在当前浏览器标签页会话中，可刷新恢复；弹窗编辑只在当前挂载期间保留，未实现跨刷新表单恢复或推荐候选的服务端历史同步。普通聊天的服务端会话仍沿用已有机制。后续聊天携带草案 ID/手选方案 ID，由后端读取可信快照并注入完整多站点上下文；非法草案/方案在进入 Agent 前拒绝，不信任客户端路线指标。此更新取代下文初版关于独立入口和候选缓存的限制描述。

## 费用与开放边界

- `AttractionFact.ticket_price_yuan` 仅允许属于有证据的已核验门票事实。金田路馆和同心路馆的既有“普通参观免费”事实补结构化 0 元；没有新增事实来源或其他消费推断。失效后清除文字结论和价格数值。南山博物馆门票仍未知。
- 有预算时先扣除已核验普通门票，余额成为 `MultiStopRequest.max_transport_cost_yuan`。全组合时间推演在排序前检查交通费用：未知为数据不足，超限为不可行。不能只筛选已返回的少数高分方案，否则可能漏掉较慢但负担得起的组合。
- 交通预算随请求进入正式规划，修改/手选分段时仍校验；页面可明确调整交通上限。它不包含餐饮、停车、购物、付费讲解和其他服务，也不能代表出行总开销保证。门票发生变化时需重新核实/调整预算。
- 对未来参观时间已超过复核期限的票价，不拿当前已核验状态保证未来费用。有预算则不纳入无法确认的馆区，不将未知当作免费。
- 现有库没有指定日期的开放核验记录。勾选“仅接受已核实指定日期开放”时，当前返回空候选和原因，且不调用路线；文本中的每周常规时间不冒充当天营业证明。普通候选是“路线约束可满足、参观安排待核实”，不是保证可参观/可预约。
- 各馆区最多 6 个相邻路线调用，当前最多 3 个馆区/18 次调用（不能驾车时更少）；每馆区整体 75 秒超时，顺序处理。扩库至超过 3 个启用馆区时明确拒绝，须先设计调用预算，不静默截断候选。本轮没有扩大库。
- 路线供应商失败只说明本次核算失败，不据此声称现实中无路线。取消向下传播；前端中止/隔离迟到结果，不保证断开 HTTP 后服务器已取消所有供应商工作。

## 兼容与状态

交通预算是可选字段；未设置时保持既有时间推演语义。方案 ID 的请求哈希在预算为空时忽略该新字段，保留旧无预算快照的标识，避免默认字段改变导致原方案身份变化。

“去哪玩”条件修改后清空旧结果，较早的搜索/推荐响应不能覆盖新条件。原多站点工作区仍使用 `multi-stop-workspace` 缓存；从“去哪玩”带入的编辑使用独立 `discovery-multi-stop-workspace` 缓存，避免覆盖原未提交表单。此首版不支持刷新后自动回到探索入口或自动恢复上次探索编辑；已确认保存的快照仍走现有重开流程。

## 第二阶段：探索天气提示与采样点排除（2026-10-23）

本节更新前文“天气尚未接入”的第一阶段状态。景点库仍为原三个馆区，没有扩库；天气也没有成为多站点评分中的新权重。

`DiscoveryRequest.weather_policy` 提供三个显式模式：

| 模式 | 行为 |
| --- | --- |
| `none`（默认） | 不调用天气服务，保持原路线/时间/预算筛选语义 |
| `inform` | 为通过原筛选的候选补充逐站报告；未知或触发提示仍保留，卡片明确提醒并可展开详情 |
| `exclude_signals` | 只保留本次推荐路线全部到达采样点有可用预报、且未触发产品提示的候选；未知不放行 |

流程仍先核验景点事实、原硬限制和路线，再为各馆区推荐方案构造内存临时草案，复用 `MultiStopWeatherService`。临时草案不写业务库、不返回重复轨迹、不重新查询路线。报告保留完整逐站信息、来源及目标/预报/查询时间，前端复用多站点天气展示组件。

补充前校验报告的方案 ID、站点顺序/数量和目标时刻是否与本次推荐路线一致。错方案、缺站、目标时间不符、超时或供应商失败均降级为未知，不泄露异常原文。原事实/路线限制已排除的馆区不会再查天气；取消继续传播，不作为有利天气吞掉。

天气定义沿用逐站服务：降水、雷暴、较高风速和体感阈值只是产品提示。排除只检查本次推荐路线的到达采样点，不比较该馆区其他路线的天气，也不覆盖整个沿途/等待/停留时段。报告未触发提示不代表全程安全、一定适宜或保证营业；未入选原因会区分未知与提示。

馆区之间仍按往返估计耗时排序；不隐式按天气重排路线或放宽预算、时间、步行、换乘限制。网页条件修改使旧候选/报告失效。选择进入正式规划后会重新查询路线，因此原天气筛选不是新方案的约束认证：卡片提示须刷新逐站天气重新核对，不把筛选报告套用到更新后的时间线上。

最多为三个候选各补一次天气报告（每份三个站点，最多三个坐标/日期请求组），每份额外 26 秒外层限时，内部仍为 25 秒/并发 2。默认不开启，用户选择时明确提示可能增加等待。没有跨候选/跨请求持久缓存或自动后台刷新，也不保证 HTTP 断开后所有服务工作立即结束。

新增后端 11 项（服务 10 项、API 1 项），前端 2 项。全量后端 **519 项**/Ruff、前端 **62 项**/lint/build 通过，仍 1 项既有第三方弃用警告。覆盖默认不查、提示保留未知、排除提示/未知、失败脱敏、错报告/缺站/时刻不符、先执行原限制、取消传播、API 注入及非法模式拒绝、页面策略提交/未知展示/切换清除/不自动放宽。模拟响应不是本轮真实天气/路线/模型或浏览器验收，未重载旧服务。
