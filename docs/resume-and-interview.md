面试官问某项技术时，优先按下面三个问题回答：

> **关键动作**。这样做的好处是 **具体收益**；它的代价或边界是 **限制**，如果场景更简单，

回答时不要只说“性能好、解耦、方便扩展”，而要把收益落到本项目，例如“服务重启后仍能恢复

## 核心技术三问速答

### Agent 项目

| 技术 | 为什么用 | 怎么用 | 带来的好处 |
| --- | --- | --- | --- |
| LangGraph | 出行任务包含多轮模型推理、连续工具调用和中途审批，普通单次调用无法保存执行状态 | 通过 `create_agent()` 构建模型—工具循环，用 `thread_id`、checkpoint、interrupt 和 `Command(resume=...)` 管理状态 | 支持多步骤任务、多轮上下文、流式事件以及服务重启后的审批恢复 |
| MCP | 天气、地点和路线能力来源不同，直接写进 Agent 会导致协议和业务代码耦合 | 将能力包装成 5 个 MCP Server、8 个带 JSON Schema 的工具，由适配器加载给模型 | 工具可发现、参数结构统一，Agent 不依赖第三方 API 的实现细节，也便于独立测试和复用 |
| Service 适配层 | Open-Meteo、OSM 和高德的字段、错误格式及坐标系不同 | Service 负责 HTTP 调用、字段映射、坐标转换和 Pydantic 校验，再返回统一 Domain 模型 | 隔离外部接口变化，更换供应商时主要修改 Service，模型只看到稳定的业务字段 |
| HITL | 保存行程会修改本地数据，不能让模型在没有授权时直接执行 | `HumanInTheLoopMiddleware` 在 `save_itinerary` 执行前暂停，前端展示参数，用户批准后再恢复图执行 | 将模型建议与真实副作用分开，支持批准、拒绝和审计，降低误操作风险 |
| SQLite checkpoint | 内存状态会在服务重启后丢失，无法继续多轮会话或待审批流程 | LangGraph 按 `thread_id` 把消息、节点状态和 interrupt 写入 `checkpoints.sqlite` | 会话与审批状态可以跨请求、跨服务重启恢复；单机简单，但多实例生产环境需迁移到共享数据库 |
| FastAPI | Agent 需要向浏览器提供聊天、流式输出、历史会话和审批接口 | 用生命周期管理 Agent 资源，以 REST/NDJSON 暴露聊天与审批能力，并配置 CORS | 将 Python Agent 变成可被前端调用的 Web 服务，接口清晰且便于测试；它本身不负责 Agent 推理 |
| NDJSON | 完整 JSON 只能在任务结束后返回，用户看不到工具调用和生成进度 | 后端逐行发送 `tool_requested`、`assistant_delta`、`final` 等 JSON 事件，前端按换行增量解析 | 实现简单的 POST 单向流式交互，并保留结构化事件；若需要长期双向实时通信再考虑 WebSocket |
| 行为评测 | 单元测试能验证函数，却不能证明模型选对工具、传对参数并完成任务 | 固定 8 类场景，检查消息轨迹、工具名、参数、工具结果和最终回答，并保存耗时、Token 与 HTTP 指标；综合规划案例额外约束不得重复调用天气工具 | 能发现 Prompt、模型或工具描述变更造成的行为回退，为技术调整提供可比较证据 |

### RAG 项目

| 技术 | 为什么用 | 怎么用 | 带来的好处 |
| --- | --- | --- | --- |
| RAG | 模型参数中没有本地文档的完整、最新知识，直接回答容易缺少依据 | 文档先解析、切分、向量化并入库；提问时检索相关 Chunk，组装上下文后交给 Qwen 生成 | 无需重新训练模型即可更新知识，回答可附来源，也能对知识边界进行控制 |
| Milvus | 项目需要对 1024 维向量执行语义相似度检索，普通关系型查询不擅长这一任务 | 保存 Chunk 向量、文本和来源元数据，使用 HNSW 索引与 COSINE 相似度搜索 Top-K | 提供面向向量的持久化和近似最近邻检索；用户权限等关系数据仍更适合关系型数据库 |
| HNSW | 全量逐个比较向量时，数据规模增大后检索成本较高 | 建立多层邻接图，查询时从高层快速定位到候选区域，再在底层细化搜索 | 用少量召回误差换取更快检索；`M`、`efConstruction` 和查询 `ef` 需要通过评测调优 |
| Chunk 与 Overlap | 整篇文档过长且主题混杂，切得过小又会破坏上下文 | 当前按 500 字符切分并保留 80 字符重叠，同时保存来源、页码和 Chunk ID | 改善检索粒度并保留跨边界语义；参数只是 Demo 基线，应按文档类型和评测结果调整 |
| Embedding 分批 | 长文档一次产生 49 个 Chunk，超过向量接口单批最多 10 段的限制 | 按 10 条一批请求 `text-embedding-v4`，保持原顺序合并，并校验数量与 1024 维度 | 支持真实长文档上传，避免整批失败，也使异常更容易定位；请求次数会相应增加 |
| Top-K 与阈值 | 仅取 Top-K 时，即使问题完全无关也会返回“最相似”的错误片段 | 先取最多 5 个候选，再用 0.40 的 COSINE 阈值过滤；过滤后为空则直接拒答 | 同时控制上下文数量与最低相关性，降低无关资料进入模型；阈值需要基于评测集继续校准 |
| 确定性拒答 | 只在 Prompt 中要求模型不要编造，仍然依赖模型是否遵守 | 检索结果为空时不调用 Qwen，代码直接返回固定答案、`grounded=false` 和空来源 | 拒答行为稳定、可测试，还能节省一次模型调用；代价是阈值过高时可能误拒答 |
| 来源引用 | 生成答案需要让用户知道依据来自哪里，而不是只相信模型文本 | 检索结果映射为 `[资料1]` 等标签，同时 API 返回文件名、页码、相似度和原文 | 用户可以核对证据，前端也能结构化展示；仍需评测引用是否真正支持对应结论 |

## 智能出行 Agent 高频问题回答要点（1-27）

### 1. 请简单介绍一下这个项目

- 用户使用自然语言完成天气、地点和多方式路线查询，并可在审批后保存行程。
- Qwen 负责理解意图与提出工具调用，LangChain 组装模型和工具，LangGraph 管理有状态执行。
- 5 个 MCP Server 暴露 8 个工具，FastAPI + React 提供流式 Web 交互。
- 可靠性设计包括 Pydantic、确定性展示、HITL、SQLite checkpoint、有限重试和行为评测。

### 2. 为什么需要 Agent

- 用户表达和任务组合不固定，可能只查天气，也可能执行地点解析 → 路线规划 → 行程保存。
- 模型适合处理自然语言意图和动态工具编排，固定 `if/else` 更适合入口和流程完全确定的业务。
- 模型不负责关键数据校验和权限；确定性代码负责业务边界与副作用控制。

### 3. 模型如何决定工具和参数

- MCP 工具向模型提供工具名称、描述和 JSON Schema。
- Qwen 根据用户消息、System Prompt、历史消息和工具 Schema 生成结构化 tool call。
- LangGraph 执行工具，把结果作为 `ToolMessage` 加回上下文，再让模型继续推理。
- LangGraph 负责执行循环，但具体选哪个工具和参数主要由模型推理产生。

### 4. 为什么使用 MCP

- MCP 标准化工具发现、参数 Schema、调用和结果返回，降低 Agent 与工具实现的耦合。
- Agent 不需要知道天气和地图服务内部使用哪个第三方 API。
- 工具可以由不同进程、语言或应用复用；代价是增加进程管理和协议调试复杂度。
- 如果只是一个不会复用的小型单体程序，直接使用普通 Tool 会更简单。

### 5. LangChain 和 LangGraph 的区别

- LangChain 是高层 Agent 框架，提供模型、消息、工具、中间件和 `create_agent()`。
- LangGraph 是有状态编排运行时，提供图执行、streaming、interrupt、checkpoint 和恢复。
- 当前 LangChain Agent 构建在 LangGraph 上；二者是不同抽象层，不是互斥选择。

### 6. LangGraph 在项目中做了什么

- 维护模型 → 工具 → 模型的消息循环。
- 按 `thread_id` 保存多轮状态。
- 在 `save_itinerary` 前触发 interrupt，通过 SQLite checkpoint 保存暂停点。
- 用户审批后使用 `Command(resume=...)` 从暂停位置继续执行。

### 7. 为什么采用四层架构

- Domain：定义统一业务模型、字段类型和校验规则。
- Service：调用第三方 API，处理超时、业务错误和字段转换。
- MCP：将 Service 包装成带 Schema 的标准工具。
- Agent：理解自然语言并动态编排工具。
- 分层隔离第三方接口、工具协议和模型行为这三类不同变化。

### 8. Service 如何统一不同接口

- 第三方原始字段只在 Service 内解析，例如 `temperature_2m` 映射为 `temperature_c`。
- Service 将原始 JSON 转换成 `CurrentWeather`、`RoutePlan` 等 Pydantic 模型。
- Pydantic 再检查类型、必填字段、非负数和经纬度范围。
- MCP 只把统一模型序列化后的 JSON 交给模型；更换供应商时主要修改 Service。

### 9. HITL 如何保护行程保存

- 模型生成 `save_itinerary` tool call 时只是提出操作及参数，工具尚未执行。
- `HumanInTheLoopMiddleware` 在工具执行前拦截并暂停 LangGraph。
- checkpoint 保存待执行操作，前端显示批准/拒绝卡片。
- 批准后恢复并真正执行写入；拒绝则跳过工具，JSONL 文件保持不变。

### 10. 为什么使用两个 SQLite 数据库

- `checkpoints.sqlite` 保存 LangGraph 内部消息、工具轨迹、节点状态和 HITL 暂停点，用于恢复执行。
- `conversations.sqlite` 保存产品可见消息、会话标题和结果卡片，用于前端历史展示。
- 两者通过 `thread_id` 关联，但把运行时内部状态与产品展示模型解耦。

### 11. 如何减少幻觉

- System Prompt 约束行为方向，但不把 Prompt 当成唯一安全边界。
- MCP JSON Schema 约束工具参数，Pydantic 校验业务数据。
- Service 统一外部数据语义，确定性展示层补充来源并限制无依据声明。
- HITL 控制副作用，固定行为评测检查工具轨迹、参数和最终回答。

### 12. 为什么需要行为评估

- 单元测试适合验证确定性的字段转换、异常处理和存储逻辑。
- Agent 行为还受模型推理影响，需要检查工具选择、参数、`ToolMessage` 和最终回答。
- 当前固定评测集统计工具选择 7/7、参数 6/6、任务完成 7/7。
- 外部服务故障标记为 `BLOCKED`，避免把基础设施问题误判为 Agent 行为回退。

### 13. 如何处理第三方 API 失败

- 网络异常、HTTP 429 和 5xx 最多尝试 2 次；普通 4xx 和明确业务错误不重试。
- 每次尝试记录服务方、方法、脱敏路径、状态码、耗时、成功状态和 attempt。
- 观测数据通过 MCP artifact 供应用和评测使用，不混入模型业务文本。
- 后续生产优化可增加缓存、熔断、降级和备用服务商。

### 14. 为什么使用 NDJSON

- 普通 JSON 必须等待整次 Agent 执行结束，无法展示工具进度和文本增量。
- NDJSON 每行一个独立事件，适合 `tool_requested`、`assistant_delta`、`final` 和审批等结构化事件。
- 当前通信是一次 POST、单向流式响应，不需要 WebSocket 的长期双向连接。
- 前端用缓冲区处理任意字节分块，再按换行解析完整 JSON。

### 15. stdio MCP 与 stdout 边界

- MCP Client 通过子进程 stdin 发送协议请求，通过 stdout 读取协议响应。
- 普通 `print()` 默认写 stdout，可能与协议消息混合并导致解析失败。
- 诊断日志应写 stderr 或日志系统，业务结果通过 MCP 返回值传输。
- stdio 适合本地单机；独立远程部署时需要采用适合网络访问的 transport。

### 16. JSONL 是什么

- JSONL 每行保存一个独立 JSON 对象，追加简单、可读，适合原型和演示。
- 当前批准保存后向 `data/itineraries.jsonl` 追加一条记录。
- JSONL 缺少数据库索引、关系、事务和成熟的多进程并发控制。
- 生产环境可迁移至 PostgreSQL，增加 `users`、`itineraries` 及所有权和权限关系。

### 17. 最难部分、不足与优化

- 主要难点：把模型驱动的保存请求改造成可暂停、可审批、可恢复且不重复写入的工作流。
- 当前不足：评测集规模较小、缺少公网鉴权和限流、JSONL 不适合多用户生产业务、尚未云端部署。
- 建议顺序：扩大评测集 → 鉴权与限流 → 缓存/熔断/降级 → 正式数据库 → Docker 和云部署。
- 回答不足时要说明边界和演进方案，不能声称当前已经具备不存在的生产能力。

### 18. 多轮上下文如何保存和恢复

- 前端在后续请求中继续携带同一个 `thread_id`，后端据此构造 LangGraph 配置。
- LangGraph checkpointer 按线程保存消息和图状态，下一次调用时恢复该线程的上下文。
- 产品可见历史另存于 `conversations.sqlite`，避免前端直接依赖 LangGraph 内部消息结构。
- 长对话仍需要进一步增加消息裁剪、摘要或长期记忆策略，避免上下文和 Token 持续增长。

### 19. 如何避免重复审批和重复写入

- 暂停状态与待审批操作绑定到 `thread_id`，审批接口先确认该线程确实存在待处理 interrupt。
- 第一次批准后图从 checkpoint 继续并完成，后续再次提交时没有待审批操作，因而拒绝重复恢复。
- 当前保证主要来自工作流状态和测试验证；生产环境还应增加幂等键、数据库唯一约束和事务。
- 不能把“当前测试中只写一次”夸大成分布式环境下已经具备严格 exactly-once 语义。

### 20. 为什么存在两种坐标系

- OpenStreetMap 地点搜索返回 WGS84；高德国内路线接口使用 GCJ-02。
- 将 WGS84 坐标直接传给高德可能产生位置偏移，影响逆地理编码和公共交通规划。
- 路线 Service 在调用高德前完成坐标转换；公交还会解析城市编码再请求路线。
- 坐标转换属于确定性基础设施逻辑，不应交给模型计算。

### 21. 工具描述和 JSON Schema 的作用

- 模型主要根据工具名称、docstring 描述和参数 Schema 判断工具用途及如何构造参数。
- 描述需要明确能力范围，例如天气工具只接受城市名，避免传入景点或完整地址。
- `Literal`、默认值和必填字段会进入 Schema，减少无效参数组合。
- Schema 是结构约束，不保证业务语义绝对正确，因此仍需 Pydantic 和 Service 校验。

### 22. 为什么选择 Qwen 和兼容接口

- Qwen 支持结构化 tool calling，能够根据工具 Schema 生成名称、参数和 call ID。
- OpenAI-compatible 接口可复用成熟的 LangChain 客户端，减少针对厂商协议的定制代码。
- 模型创建集中在独立模块，业务 Service 与 MCP 工具不依赖具体模型供应商。
- 如果替换模型，需要重新运行行为评测，不能只验证接口能够连接。

### 23. 如何防范 Prompt Injection 和越权调用

- 不把用户文本直接拼接成系统命令、文件路径或 SQL，工具只接受受限的结构化参数。
- 用 System Prompt 声明能力边界，但关键权限不能只依赖 Prompt。
- 写操作经过 HITL；Pydantic、`Literal` 和 Service 校验限制参数范围。
- 公网生产环境还需要用户鉴权、资源所有权检查、速率限制、审计和更细粒度的工具权限策略。

### 24. 如何优化延迟和成本

- 减少不必要的工具描述和历史消息，长会话可采用裁剪或摘要。
- 对稳定的地点解析结果设置合规缓存，避免重复调用第三方服务。
- 可以并行执行相互独立的只读工具，但存在依赖关系的步骤仍需顺序执行。
- 通过评测报告同时观察任务正确率、平均耗时、Token 和 HTTP 次数，避免只优化单一指标。

### 25. 如何隔离真实模型和外部服务进行测试

- Service 接受外部 `httpx.AsyncClient`，测试时注入 `MockTransport` 返回固定响应。
- 单元测试分别覆盖 Domain 校验、Service 转换、MCP 包装、展示策略和存储。
- 前端使用 Vitest 和 React Testing Library 模拟 NDJSON 流、审批和历史会话接口。
- 真实模型与真实网络留给行为评测和冒烟测试，避免普通单元测试不稳定且产生费用。

### 26. 为什么 CI 不运行真实 Agent 评测

- GitHub 公共 CI 不应持有个人开发环境的真实 API Key，也不应在每次 push 时产生模型费用。
- 第三方天气和地图服务波动会使 CI 出现与代码无关的偶发失败。
- CI 运行可重复的 Ruff、Pytest、前端测试、lint 和 production build。
- 真实行为评测作为受控任务运行，生成报告后再与基线比较；生产团队可使用受保护 Secrets 和定时任务扩展。

### 27. 多用户生产架构如何演进

- 使用 PostgreSQL 保存用户、会话和行程，以唯一约束和事务支持权限、幂等及并发。
- 引入登录鉴权、租户隔离、速率限制、API 配额和审计日志。
- 将 Web API、Agent worker 和 MCP/外部服务适配拆分，并使用任务队列处理长时间运行任务。
- 使用容器、反向代理、HTTPS、集中式日志、指标、trace、缓存、熔断和降级策略。
- 部署前扩充离线与在线评测集，并针对模型、Prompt、工具或供应商变更设置回归门槛。

## RAG 知识库助手回答要点（28-44）

### 28. 请简单介绍 RAG 项目

- 这是一个面向本地文档的可追溯知识库问答系统，支持 PDF、Word、Markdown 和 TXT。
- 索引阶段完成解析、切分、分批向量化和 Milvus 入库；查询阶段完成问题向量化、Top-K 检索、阈值过滤和 Qwen 生成。
- 回答携带来源片段和相似度；资料不足时确定性拒答。
- FastAPI + React 提供文档上传、知识问答和来源展示，Milvus 使用 Docker Compose 运行。

### 29. 索引阶段和查询阶段

- 索引：文档解析 → 重叠切分 → `text-embedding-v4` 向量化 → Milvus 存储向量、文本和来源元数据。
- 查询：问题向量化 → Milvus HNSW 近似检索 → 阈值过滤 → 组装参考资料 → Qwen 生成带引用回答。
- 索引是上传或更新文档时执行，不是每次提问都重新解析全部文档。

### 30. 为什么使用 RAG

- 大模型参数中不一定包含企业私有、本地或最新资料。
- RAG 在提问时动态检索外部知识，无需为每次文档变更重新微调模型。
- 来源元数据使回答可追溯，便于用户核对。
- RAG 不保证资料本身正确，知识库内容仍需要治理和更新。

### 31. 为什么使用 Milvus

- Milvus 面向高维向量存储和近似最近邻检索，可直接建立 HNSW 索引。
- 普通关系型数据库更擅长结构化过滤、事务和关联查询，默认不擅长大规模高维相似度检索。
- 生产系统中可以同时使用关系型数据库管理用户和权限，用 Milvus 管理向量。

### 32. HNSW 和 COSINE 的作用

- HNSW 是近似最近邻索引，通过多层图结构减少需要比较的向量数量，提升检索速度。
- COSINE 通过向量方向的夹角衡量语义相似度，较少受向量长度影响。
- 项目使用 `M=16`、`efConstruction=200`，查询 `ef=64`；这些参数是效果、速度和内存的折中，不是通用最优值。

### 33. Chunk Size 和 Overlap 如何选择

- Chunk 太大容易混入无关内容，占用更多上下文；太小则容易丢失语义和跨边界信息。
- 当前 `500/80` 是 Demo 的初始参数，重叠用于保留切分边界附近的上下文。
- 真实业务应按文档类型、问题长度、召回率和答案正确率做分组评测，不应只凭经验确定。

### 34. 1024 维 Embedding 是什么

- 向量模型把文本映射为 1024 个浮点数，数值共同表示文本的语义特征。
- 向量维度由模型和请求配置决定，Milvus Collection 的向量字段维度必须与其一致。
- 更高维度可能表示更多信息，但也会提高存储、计算和索引成本，效果并非必然更好。

### 35. 长文档上传失败的定位与修复

- 示例文档只有 1 个 Chunk，而真实 Markdown 被分成 49 个 Chunk，暴露了批次上限问题。
- `text-embedding-v4` 单批最多处理 10 段，原代码一次提交 49 段导致失败。
- 修复后按 `10+10+10+10+9` 分批请求，再按原顺序合并向量，并增加返回数量和维度校验。
- 同时将后端未捕获异常转为可读的 502 响应，避免前端只显示 `Failed to fetch`。

### 36. Top-K 与阈值如何配合

- Top-K 控制候选片段的最大数量，当前默认取 5 个。
- 阈值再移除语义相关性不足的候选，当前 COSINE 相似度阈值为 `0.40`。
- Top-K 太小可能漏召回，太大可能引入噪声并增加 Token；阈值过高容易拒答，过低容易引入无关资料。
- 参数需根据标注评测集调优，当前值只是 Demo 基线。

### 37. 来源引用如何生成

- Milvus 中除了向量，还存储 `chunk_id`、`source_name`、页码和文本内容。
- 检索结果按顺序转换为 `[资料1]`、`[资料2]` 等确定性标签，并与参考资料一起提供给 Qwen。
- 最终 API 同时返回模型文本和结构化 `sources`，前端展示文件名、页码、相似度和原文。
- 模型生成的引用标记仍需评测，不能仅靠 Prompt 保证绝对一致。

### 38. 资料不足时如何拒答

- 系统先检索，再使用确定性代码筛选达到阈值的 Chunk。
- 如果筛选后为空，则不调用 Qwen，直接返回固定的“知识库中没有足够相关的资料”。
- 返回中 `grounded=false`、`sources=[]`，前端据此展示“知识库依据不足”。
- 这比只在 Prompt 中要求模型“不要幻觉”更可测、更可控。

### 39. 同名文档如何更新

- 文档解析、切分和 Embedding 先完整成功，避免向量服务失败时提前删除旧数据。
- 随后按 `source_name` 删除 Milvus 中的旧 Chunk，再 upsert 新 Chunk 并 flush。
- 当前以文件名作为替换边界，适合单知识库 Demo；多租户环境应引入 `tenant_id` 和 `knowledge_base_id`。
- 更严格的生产方案还需要版本号、事务或蓝绿 Collection 切换。

### 40. 多格式文档如何统一

- Loader 将不同文件统一转换为 `DocumentPart`，包含文档 ID、来源文件名、部分序号、页码和文本。
- PDF 按页解析，Word 合并非空段落，Markdown/TXT 读取文本内容。
- 下游 Chunker、Embedding 和 Milvus 只依赖统一模型，不需要感知原始文件类型。
- 统一模型便于添加新 Loader，也方便实现来源引用。

### 41. 外部依赖不可用时如何处理

- FastAPI `/health` 检查 Milvus Collection 和 Chunk 数量，前端展示在线状态。
- 上传中的 DashScope 或 Milvus 错误会转换为 502 可读响应，避免泄露完整内部异常。
- Milvus 由 Docker Compose 管理，组件包括 etcd、MinIO 和 standalone；主容器异常退出时可用 `docker compose up -d` 恢复持久化数据。
- 生产环境还应增加超时、有限重试、指标监控、告警和降级。

### 42. RAG 行为评测与单元测试的区别

- 单元测试使用假客户端验证文档转换、分批、阈值、API 错误和 Milvus 结果解析等确定性逻辑。
- RAG 行为评测使用真实 Embedding、Milvus 和 Qwen，检查相关问题、引用和无关问题拒答。
- 评测会创建独立临时 Collection，只写入固定样例文档，避免被用户上传的正式知识库干扰。
- 当前 20 项自动化测试和 3 类核心 RAG 行为评测通过，但评测集规模仍需扩大。

### 43. 当前不足和生产化方向

- 当前是单 Collection、单用户 Demo，缺少账号、多租户、知识库权限和文档版本管理。
- 检索仅使用稠密向量，可增加 BM25 + 向量的混合检索、Reranker 和 Query Rewrite。
- 大文档应改为后台任务，增加任务状态、失败重试、并发控制和资源配额。
- 需要扩充检索指标（Recall@K、MRR）、答案忠实度和引用正确性评测，并加入可观测性。

### 44. RAG 与 MCP 的区别

- RAG 解决“模型如何从外部文档获取相关知识”，核心是向量化、检索、上下文组装和可追溯生成。
- MCP 解决“模型如何用统一协议发现和调用外部工具”，核心是工具 Schema、协议通信和能力解耦。
- 智能出行项目强调动态工具选择、多步编排和 HITL；知识库项目强调文档索引、检索质量、引用与拒答边界。
- 两者可以组合：把知识库检索封装为 MCP Tool，供 Agent 在复杂工作流中调用。

## 充电需求研究回答要点（45-52）

### 45. 请简单介绍研究

- 研究以深圳市交通分析区为空间单元，结合充电记录、电价机制和城市 POI 等数据解释充电需求差异。
- 通过改进 LDA 从 POI 提取城市功能主题，再按定价机制和时段构建 XGBoost 需求模型。
- 使用 SHAP 和 PDP 分析全局影响、局部贡献和非线性阈值。
- 结果用于识别不同定价区域的需求机制以及部分区域的充电设施供需错配。

### 46. 为什么使用 LDA

- POI 类型维度较多且存在共现，直接使用单个 POI 计数可能维度高、相关性强且难以概括区域功能。
- LDA 将一个交通分析区表示为多个潜在城市功能主题的混合分布。
- 主题特征既完成降维，又保留了区域功能的语义，便于后续需求建模和解释。
- 主题数和解释需结合指标、主题稳定性和城市语义共同判断。

### 47. 为什么使用 XGBoost

- 充电需求与电价、时间、城市功能和设施之间可能存在非线性和交互关系。
- XGBoost 能够处理非线性、特征交互和不同尺度特征，通常比单纯线性回归更适合该类表格数据。
- 树模型还可与 SHAP 高效结合，用于分析特征对单个样本和整体模型的贡献。
- 选择模型不只看单次最高指标，还要与线性模型等基线在同一划分下比较。

### 48. 如何避免时空数据泄漏

- 不应对相邻时刻的行随机拆分，否则同一天或相邻时间的高相关样本可能同时进入训练和测试。
- 更安全的方法是按日期分组，并按时间顺序将较早日期用于训练、较晚日期用于测试。
- 所有特征工程、缺失值填补和参数调整都应在训练数据内拟合，不能利用测试期信息。
- 若研究目标是空间泛化，还应增加按区域留出的验证。

### 49. SHAP 和 PDP 的区别

- SHAP 基于边际贡献分配，可以解释单个样本中各特征如何推高或降低预测，也可汇总全局重要性。
- PDP 通过对其他特征取平均，展示目标特征改变时模型预测的平均响应曲线。
- SHAP 更适合分析贡献方向和异质性，PDP 更直观地展示非线性趋势和可能阈值。
- 当特征高度相关时，PDP 可能生成不现实的特征组合，SHAP 解释也应谨慎区分关联与因果。

### 50. 如何解释 R²=0.928

- 该指标表示在当前动态定价区域的特定测试集上，模型解释了约 92.8% 的目标方差。
- 它不表示预测误差只有 7.2%，也不代表所有区域、时段和未来数据上都能达到该水平。
- 应与 MAE、RMSE、残差分布和不同时间/区域分组指标结合解读。
- 面试时要说清评测数据范围与划分方式，避免把单个子集指标夸大为普遍结论。

### 51. 如何识别阈值和供需错配

- 夜间电价敏感阈值主要通过 PDP 或 SHAP Dependence Plot 观察模型响应在某一取值附近的斜率或方向变化。
- 阈值是模型在当前数据上学到的非线性特征，需结合置信区间、样本分布和稳健性检验，不能直接解释为因果阈值。
- 供需错配可通过区域预测需求、实际充电量、设施数量和利用率的对照识别。
- 对异常区域还应回到时间、TAZ 和定价分组做明细核查，避免只看总体平均。

### 52. 研究局限和改进方向

- 观测数据与树模型解释主要反映关联关系，不能直接得出电价或 POI 的因果效应。
- 数据受城市、时间范围、缺失值和充电运营平台覆盖范围限制，跨城市和跨时期泛化需另行验证。
- 后续可加入天气、节假日、交通、充电站排队和更细的电价变化数据。
- 方法上可增加时空交叉验证、因果推断或准实验设计，并检验解释结果的稳定性。

## 综合面试高频问题（53-57）

### 53. 为什么同时做 Agent 和 RAG 两个 AI 项目

- 两个项目覆盖大模型应用的两条主要落地路线：Agent 负责工具调用和复杂工作流，RAG 负责外部知识检索和可追溯问答。
- 前者重点是 LangGraph、MCP、HITL 和状态持久化；后者重点是文档处理、Embedding、Milvus、阈值和引用边界。
- 两者都从 Demo 扩展到 FastAPI/React、测试、行为评测和 CI，体现的是完整工程落地能力。

### 54. 项目中最有代表性的问题定位经历

- Agent 项目中，典型问题是将有副作用的保存调用改造为可暂停、审批、恢复且避免重复写入的 HITL 工作流。
- RAG 项目中，典型问题是样例文档成功但真实长文档失败，最终通过 Chunk 数量和供应商批次限制定位到分批向量化缺失。
- 面试时按“现象 → 缩小范围 → 根因 → 修复 → 测试固化”的顺序讲述。

### 55. 如何证明项目不只是页面 Demo

- 展示稳定的 Domain/Service/API 或 Domain/Service/MCP/Agent 分层，而不只展示前端截图。
- 展示真实外部服务、错误处理、持久化、安全边界和数据来源。
- 展示可重复的 Pytest、Agent/RAG 行为评测报告以及 GitHub Actions CI。
- 主动说明当前边界和生产化方向，避免将局部测试结果夸大为全面生产能力。

### 56. 实习中可以承担什么工作

- 能够承担 Python 后端与大模型应用功能开发，包括工具封装、RAG 检索链路、FastAPI 接口和基础前端联调。
- 能够针对第三方 API、模型输出和数据转换建立校验、错误边界和自动化测试。

- 对暂时不熟悉的业务，会先明确数据边界和验收标准，再小步实现与验证。
